# Roadmap MVP iOS-клиента VPN-сервиса

Дата: 2026-07-06. Основано на карте клиентского API (`ios_client_api_map.md`) и анти-РКН-ограничениях проекта.

Цель MVP: удобный нативный клиент под iOS/iPadOS с качественным UX, надёжной сетевой логикой, диагностикой подключения и автоматическим выбором оптимальной конфигурации по доступности и качеству связи. Без лишних фич — минимальный контур, который стабильно держит соединение в условиях РКН-DPI.

---

## 0. Ключевое решение: транспортное ядро

Клиент не пишет VPN-протоколы сам — он встраивает готовое прокси-ядро внутрь `NEPacketTunnelProvider`. Требования к ядру заданы бэкендом:

- Протоколы: **VLESS Reality (xtls-rprx-vision)**, VLESS XHTTP, VLESS WS, Hysteria2. Значит ядро — **Xray-core** или **sing-box** (оба умеют весь набор). sing-box предпочтительнее: активнее развивается, нативная библиотека под iOS (`Libbox`), встроенный url-test/selector для client-side failover, чище API.
- **Обязательно uTLS fingerprint = firefox** (`fp=firefox`). Core должен уметь ставить именно этот отпечаток (chrome/safari/ios палятся DPI).
- Импорт стандартной **base64-подписки** (`/api/sub/{token}`) — оба ядра едят её нативно.

**Вывод:** MVP = SwiftUI-оболочка + sing-box (Libbox) в PacketTunnelProvider. Ядро тянется как бинарный `.xcframework` (собирается из sing-box отдельно, вне App Store). Это снимает 80% сетевой сложности — ретраи/url-test/переключение нод делает ядро.

## 1. Архитектура MVP

Приложение = **основной таргет (UI + логика)** + **PacketTunnel-расширение (сетевое ядро)** + **общий framework (модели, конфиг, логи)**. Расширение — отдельный процесс с жёстким лимитом памяти (~50 МБ на старых устройствах), поэтому тяжёлое держим в основном приложении.

```
VPNApp/                        основной таргет (SwiftUI)
  App/                         точка входа, роутинг сцен
  Features/
    Onboarding/                ввод sub-ссылки / QR / deep-link
    Home/                      главный экран: тумблер + статус + текущая нода
    Diagnostics/               экран диагностики соединения
    Settings/                  минимум: об аккаунте, ссылка на бота, логи
  Core/                        бизнес-логика (в общий framework)
    TunnelController           старт/стоп/статус через NETunnelProviderManager
    SubscriptionStore          загрузка/кэш sub-ссылки, парсинг URI
    ConfigBuilder              sub-URI → sing-box config (outbounds + url-test)
    HealthReporter             self-report сбоя в control-channel
    Diagnostics                локальные пробы (пинг/HTTP-проба через ноду)
PacketTunnelExtension/         NEPacketTunnelProvider
  TunnelProvider               поднимает sing-box (Libbox), проксирует пакеты
Shared/ (framework)
  Models                       Subscription, NodeEndpoint, Protocol, Status
  ConfigSchema                 типобезопасная модель sing-box config
  Logging                      структурный лог в App Group (общий с расширением)
  Keychain                     sub_token, client_id_hmac (secure enclave)
```

### 1.1 UI-слой (SwiftUI)
Тонкий: только рендер состояния из `TunnelController.status` (Combine/`@Observable`) и вызов команд. Никакой сетевой логики в вьюхах. Три экрана в MVP: Onboarding → Home → Diagnostics; Settings — вторично.

### 1.2 Core-логика
- **TunnelController** — единственный владелец `NETunnelProviderManager`: `install()` (первый раз — запрос разрешения VPN), `start()`, `stop()`, подписка на `NEVPNStatusDidChange`. Статусы транслирует в доменную модель (`.disconnected/.connecting/.connected(node)/.reasserting/.failed(reason)`).
- **SubscriptionStore** — тянет `/api/sub/{token}`, уважает заголовки: `profile-update-interval` (когда рефрешить), `subscription-userinfo: expire=` (срок), `profile-title`. Кэширует последнюю УСПЕШНУЮ сабу; на `503`/сеть-ошибке НЕ перезаписывает кэш пустотой (бэкенд специально шлёт 503 вместо пустого 200). На `fallback-url` из заголовка — запасной источник сабы, если основной домен режется.
- **ConfigBuilder** — из списка URI строит sing-box config: каждый URI → outbound; поверх — **url-test outbound** (авто-выбор по наименьшей задержке) + **selector** (ручной выбор ноды). Это и есть client-side failover по N×M diverse-сабе (см. §2.4).

### 1.3 Сетевой слой
Внутри расширения: sing-box держит все outbound'ы, url-test периодически пингует их (`/api/sub` уже отдаёт несколько нод при `DIVERSE_SUB_NODES>1`), трафик идёт через лучший. Приложение сетью почти не занимается — только (а) рефреш сабы и (б) self-report.

### 1.4 Слой конфигурации
`Subscription` (sub_token, expire, набор `NodeEndpoint`) кэшируется в App Group (доступен расширению). Обновление: по таймеру `profile-update-interval`, при ручном pull-to-refresh, и при `action=migrated` от self-report. Частично невалидная саба (одна битая строка URI) — **не роняет всё**: парсер пропускает нечитаемые строки, логирует, строит config из валидных.

### 1.5 Диагностика
Локальные пробы (не требуют бэкенд-изменений для MVP):
- статус ядра (connected/handshake-failed/timeout) из Libbox;
- per-node задержка из url-test;
- HTTP-проба через туннель (запрос к нейтральному 204-эндпоинту) → «интернет есть/нет через VPN»;
- сравнение с прямым коннектом → локализация «VPN мёртв vs сеть мёртва».
Плюс кнопка «Сообщить о проблеме» → self-report в control-channel.

### 1.6 Логирование
Структурный лог (os_log + файл в App Group, ring-buffer ~1 МБ). Расширение и приложение пишут в один файл. Экран Settings → «Поделиться логами» (для поддержки в боте). Без PII в логах (только node id/proto/latency, не sub_token).

### 1.7 Обновление настроек
`profile-update-interval` (дефолт 6 ч) — фон-рефреш сабы через `BGAppRefreshTask`. При смене конфига на бэкенде (миграция ноды) клиент подтянет новый набор при следующем рефреше или после self-report.

### 1.8 Обработка ошибок
Единая доменная модель ошибок → понятные статусы (см. §5). Сетевые ошибки рефреша — тихий ретрwith backoff, кэш не трогаем. Ошибки старта туннеля — явный статус + «Диагностика». Истёкшая подписка (`expire` в прошлом или `403` от сабы) → экран «Подписка истекла» со ссылкой на бота.

## 2. Основные функции MVP

### 2.1 Подключение к инфраструктуре
Тумблер на Home: `TunnelController.start()`. Первый запуск — системный диалог разрешения VPN (NetworkExtension). Дальше — один тап.

### 2.2 Получение пользовательской конфигурации
Онбординг по **sub-ссылке**: три пути — вставка ссылки, скан QR (бот отдаёт QR), **deep-link** (`vpnapp://import?url=...` из бота — самый гладкий UX, один тап из Telegram). Токен и производный `client_id_hmac` кладём в Keychain. **Кабинет/оплата — в MVP НЕ нативные**: кнопка «Управление подпиской» открывает Telegram-бота/webapp (нативного клиент-API вне Telegram сейчас нет, см. дырку в карте).

### 2.3 Проверка доступности
url-test ядра непрерывно меряет задержку всех нод набора. Приложение показывает «проверка…» пока нет ни одного живого outbound.

### 2.4 Автовыбор оптимального подключения
sing-box **url-test outbound**: автоматически берёт ноду с наименьшей задержкой из N×M diverse-сабы, перепроверяет с интервалом, при деградации сам переключается — **без обращения к бэкенду**. Это готовая client-side отказоустойчивость. Ручной selector — на экране Diagnostics (выбрать конкретную ноду).

### 2.5 Базовый fallback
Три уровня:
1. **Внутри набора** — url-test прыгает между нодами (мгновенно, ядро).
2. **Источник сабы** — если сам sub-URL режется, берём `fallback-url` из заголовка ответа.
3. **Self-report** — если весь набор мёртв, `POST /api/client/report-failure` → бэкенд мигрирует юзера на свежую ноду; клиент уважает `retry_after_sec`, затем рефрешит сабу и переподнимает туннель.

### 2.6 Диагностика проблем
Экран Diagnostics (§1.5): показывает, что именно не так, и предлагает действие (переключить ноду / сообщить о проблеме / проверить сеть).

### 2.7 Понятные статусы
См. §5 — конечный автомат статусов с человеческими формулировками, без технического жаргона в основном потоке.

### 2.8 Простой онбординг
Один экран: «Вставьте ссылку из бота» + большая кнопка + «Открыть бота». Deep-link из Telegram минует ввод вообще. После импорта — сразу Home с призывом «Подключиться».

## 3. Ограничения iOS

### 3.1 Системные
- **NetworkExtension entitlement** (`com.apple.developer.networking.networkextension` → `packet-tunnel-provider`) — требует Apple Developer Program и **явного одобрения Apple** (запрашивается через форму; для VPN-приложений выдаётся, но не мгновенно — заложить время). Это блокер релиза, но НЕ разработки (в dev-режиме работает на устройстве с provisioning profile).
- **Расширение — жёсткий лимит памяти** (~15 МБ гарантированно, до ~50 МБ). sing-box укладывается, но: не держать в расширении парсинг/логику UI, конфиг передавать готовым через `providerConfiguration`.
- **Фоновые обновления** — только `BGAppRefreshTask` (система решает когда; нельзя гарантировать точный интервал). Рефреш сабы — best-effort в фоне + обязательный при выходе из фона.
- **Нет доступа к «сырому» списку Wi-Fi/смене сети напрямую** — но `NWPathMonitor` даёт события смены сети (Wi-Fi↔LTE), по ним переустанавливаем туннель/перезапускаем url-test.
- **On-demand rules** (`NEOnDemandRule`) — авто-подключение по условиям; в MVP опционально.

### 3.2 Разрешения
- VPN-конфигурация (системный диалог при первом `start`).
- Уведомления (опционально — для «соединение упало»).
- Камера (только если делаем QR-скан — можно отложить, оставив вставку ссылки/deep-link).
- Local Network — обычно не требуется для tunnel provider.

### 3.3 Что отложить за MVP
- Нативный кабинет/оплата (нужна новая auth-схема вне Telegram — см. §6).
- Показ остатка трафика/квоты (бэкенд не отдаёт `upload/download/total` в сабе — только `expire`).
- On-demand auto-connect, per-app VPN, виджеты, Apple Watch.
- Push «нода упала» (нужен push-эндпоинт).
- Измерительная телеметрия качества (нет measurement-эндпоинта).

### 3.4 Что подходит для MVP
Импорт по sub-ссылке, sing-box-ядро с url-test, локальная диагностика, self-report сбоя, фон-рефреш сабы, понятные статусы — всё это реализуемо **без единого изменения бэкенда**.

## 4. Roadmap (этапы)

| Этап | Содержание | Результат |
|------|-----------|-----------|
| **0. Исследование** | Собрать sing-box как iOS `.xcframework` (Libbox), проверить fp=firefox + Reality vision на реальной ноде; запросить NetworkExtension entitlement у Apple | Ядро подключается к прод-ноде из PoC |
| **1. Архитектура** | Каркас проекта (3 таргета + App Group + Keychain), доменные модели, `TunnelController` поверх NETunnelProviderManager, пустой PacketTunnelProvider | Туннель поднимается/гасится, статус в UI |
| **2. MVP-контур** | Онбординг по sub-ссылке + deep-link, `SubscriptionStore` (загрузка+кэш+заголовки), `ConfigBuilder` (sub-URI → sing-box config с url-test), реальное подключение | Вставил ссылку → подключился → ходит трафик |
| **3. Диагностика** | Экран Diagnostics, локальные пробы, per-node latency, HTTP-проба через туннель, ручной selector ноды | Юзер видит, что не так, и может переключить ноду |
| **4. Надёжность** | Реакция на смену сети (`NWPathMonitor`), self-report + обработка `retry_after_sec`+рефреш, fallback-url, устойчивый парсинг частично битой сабы, фон-рефреш (`BGAppRefreshTask`) | Соединение переживает смену сети/блок ноды без ручных действий |
| **5. UX/UI** | Apple-like визуал (§7), конечный автомат статусов, анимации перехода, пустые/ошибочные состояния, онбординг-полировка | Интерфейс ощущается «системным» |
| **6. Тестирование** | Юнит: парсер URI, ConfigBuilder, статус-машина, обработка заголовков сабы. Интеграция: подключение к тест-ноде. Ручное: смена сети, потеря связи, истёкшая саба, битая строка | Зелёные тесты логики + чек-лист ручных сценариев |
| **7. Релиз** | Одобренный entitlement, App Store privacy-манифест, скриншоты, описание (осторожно с формулировками про обход), TestFlight-бета | Сборка в TestFlight → App Store |

Порядок жёсткий: этап 0 (ядро+entitlement) — блокер всего; 2 нельзя без 1; 4 опирается на 3.

## 5. Статусы для пользователя (конечный автомат)

| Состояние | Что показать | Действие |
|-----------|--------------|----------|
| `disconnected` | «Отключено» + большая кнопка «Подключиться» | tap → connect |
| `connecting` | «Подключение…» + спиннер | — |
| `connected(node)` | «Защищено» + страна/город ноды + задержка | tap → disconnect |
| `reasserting` | «Переключаемся на лучший сервер…» (смена ноды url-test'ом/сеть сменилась) | — |
| `noWorkingNode` | «Серверы недоступны. Пробуем восстановить…» + авто self-report | «Сообщить о проблеме» |
| `subscriptionExpired` | «Подписка истекла» | «Продлить в боте» |
| `failed(reason)` | человеческая причина + «Открыть диагностику» | Diagnostics |

Правило: в основном потоке — простые формулировки; технические детали (какой протокол, какая нода, код ошибки) — только на экране Diagnostics и в логах.

## 6. Дырки бэкенда, влияющие на iOS (для планирования, не блокеры MVP)

Из карты API — чего сейчас нет; MVP обходится без них, но для полноценного продукта понадобится:
1. **Нативная auth вне Telegram** — для кабинета/оплаты в приложении (сейчас всё через Telegram initData). MVP: кабинет открывается в боте/webapp.
2. **Трафик-квота в сабе** — `subscription-userinfo` несёт только `expire`. Нельзя показать «осталось X ГБ».
3. **Measurement/quality-report эндпоинт** — клиент не может слать latency/loss-метрики. Есть только бинарный self-report «сломалось».
4. **`report-failure` не отдаёт новую сабу** — клиент сам передёргивает sub-ссылку после `action=migrated`.
5. **Control-channel требует shared `APP_SECRET_KEY`** — опасно зашивать в iOS-бинарь. Для self-report из нативного клиента нужен per-client секрет/подпись (сейчас в проде секрет подаётся через CF Worker-посредник). **Для MVP:** либо ходить в control-channel через тот же Worker-прокси, либо в MVP ограничиться client-side failover (url-test) без серверного self-report, добавив его во вторую итерацию.

## 7. Дизайн (Apple-like)

- **Визуальный язык:** нативный SwiftUI, системные материалы (`.regularMaterial`), San Francisco, крупный тумблер-«герой» на Home как смысловой центр (по образцу системного VPN-тумблера, но крупнее и с явным статусом-цветом: серый→жёлтый→зелёный).
- **Минимализм:** один основной экран, одна главная кнопка. Всё остальное — вторично и вглубь.
- **Иерархия:** статус — самый крупный элемент; нода/задержка — подпись; управление — ниже. Диагностика и настройки — не на первом экране.
- **Отступы:** системная сетка (16/20 pt), крупные тач-цели (≥44 pt), дышащие поля.
- **Минимум действий:** подключение — один тап; онбординг — один экран/один deep-link; переключение ноды — авто (ручное спрятано в Diagnostics).
- **Статусы и ошибки:** цветовая семантика (зелёный=защищено, жёлтый=переключение, красный=проблема), человеческий текст, всегда рядом — действие («Сообщить», «Продлить», «Диагностика»). Никаких голых кодов ошибок в основном потоке. Плавные переходы состояний (краткая анимация тумблера/цвета), тактильный отклик на connect/disconnect.

---

> MVP реализуем **без изменений бэкенда**: sub-ссылка + sing-box(url-test) + локальная диагностика + (опц.) self-report через существующий control-channel-прокси. Серверные дырки (§6) — во вторую итерацию.
