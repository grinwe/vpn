# План технического аудита кодовой базы VPN-сервиса

Дата: 2026-07-04. Ветка: `dev` (аудит по состоянию рабочей копии на диске, включая незакоммиченные правки).

## 1. Рамки

**В рамках этого прохода:** качество кода, архитектура, надёжность, обработка ошибок, тестируемость, поддерживаемость, производительность.

**Вне рамок (по договорённости):** безопасность, threat model, уязвимости, авторизация, работа с секретами. Исключение: краши и некорректное поведение из-за невалидного ввода — это вопрос надёжности, он в рамках.

Отдельными шагами после основного аудита (по списку задач в `audit.md`):
1. Аудит сетевой логики (надёжность, корректность, UX) → отдельный отчёт.
2. Roadmap MVP мобильного клиента для Apple-платформ → отдельный документ.

## 3. Методология

Многоагентный аудит с адверсариальной верификацией:

1. **Разведка** — карта репозитория, объёмы, границы подсистем (сделано).
2. **Параллельный поиск** — 22 независимых агента: 16 «зонных» (каждый глубоко читает свою подсистему) + 6 «сквозных линз» (асинхронность/гонки, обработка ошибок и логирование, архитектура, поддерживаемость, производительность, тесты). Каждая находка обязана иметь evidence — цитату кода с точным `file:line`.
3. **Дедупликация** — слияние находок, найденных несколькими агентами.
4. **Адверсариальная верификация** — каждую находку проверяет отдельный агент-скептик, задача которого — *опровергнуть* её по коду. Для подтверждённых Critical/High — второй независимый голос. Не подтверждённые полностью находки помечаются, опровергнутые — выносятся в список отклонённых (для прозрачности).
5. **Отчёт** — сборка по формату ниже.

Правила: не выдумывать факты; всё, что не доказано кодом, явно помечается как предположение. Намеренные архитектурные решения (например, инвариант sub-ссылок с сохранением отозванных устройств) не считаются дефектами.

## 4. Шкалы

**Критичность:**
- **Critical** — падение сервиса, потеря данных или массовый отказ в реалистичном сценарии.
- **High** — серьёзный сбой или деградация надёжности в реалистичном сценарии.
- **Medium** — сбой в edge-case; заметный риск регрессий при изменениях.
- **Low** — качество кода без прямого влияния на работу.

**Приоритет внедрения:** P0 — немедленно; P1 — ближайшие 1–2 недели; P2 — планово в течение квартала; P3 — по возможности.

**Сложность исправления:** S — до 2 часов; M — до дня; L — несколько дней.

## 5. Формат карточки находки

```
### <N>. <Название> — <критичность>, <приоритет>, сложность <S/M/L>
Где: file:line (подсистема)
Что происходит: описание простым языком
Почему это важно: последствия для сервиса/пользователей/разработки
Как исправить: суть решения
План исправления: пошагово
[⚠️ не подтверждено полностью — если верификация дала «вероятно», а не «доказано»]
[Помечено как предположение — если вывод не доказан кодом]
```

## 6. Структура отчёта (`docs/audit/code_audit_report.md`)

1. Резюме: общая оценка, сводная таблица Critical/High, топ quick wins, рекомендованная последовательность работ.
2. Архитектура и границы модулей (обзор + находки).
3. Находки по подсистемам: Backend API → Provisioning/worker → Ноды и облака → Health/диагностика → Биллинг → Модели и сервисы → Бот → Frontend → Ansible → Тесты.
4. Сквозные срезы: асинхронность, обработка ошибок/логирование, поддерживаемость, производительность.
5. Методология и ограничения аудита; список отклонённых верификацией находок — внутри секций.

Отчёт по сетевой логике (`docs/audit/network_audit_report.md`) использует те же шкалы и карточки, плюс поле «влияние на пользователя».
