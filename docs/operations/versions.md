# Версии: код, ноды, xray, hysteria

Раньше на два вопроса — «какой код сейчас на проде» и «на каких нодах какое ядро
xray» — ответить было нечем. `.git` вырезается при rsync, образы собираются на
самом хосте без тегов, а фактическая версия xray жила только в stdout
ansible-таски и умирала вместе с ней. Обновление флота держалось в голове: где
перекатили, где нет.

Теперь версии видны в админке (страница **Версии** и бейдж в строке ноды на
**Nodes**). Продуктов два: три VLESS-протокола (Reality, XHTTP, WS-CDN) держит
**один** бинарь xray — три systemd-юнита, один исполняемый файл, — а hysteria2
это отдельный демон `hysteria-server` со своим релиз-циклом. Поэтому и пин, и
сбор, и кнопка апгрейда у них раздельные.

## 1. Версия нашего кода

Единственный источник правды — файл **`VERSION`** в корне репозитория. Одна
семверная строка на весь проект: она же версия бэкенда, ansible-ролей и обоих
фронтов. Бампается **руками** перед выкатом.

Почему не git sha: деплой катает рабочее дерево, а не коммит (`deploy_app_stack`
делает `synchronize` из `deploy_app_stack_repo_src`), поэтому sha врал бы при
выкатке с незакоммиченными правками — а это здесь обычная практика.

Как значение доезжает:

| Куда | Как |
|---|---|
| `.env` на прод-хосте | `deploy_app_stack` читает `VERSION` на контроллере → `APP_VERSION` |
| backend / worker | env `APP_VERSION`, читает `app/version.py` |
| админка, webapp | build-arg `VITE_APP_VERSION` (Vite запекает в бандл) |
| ноды | extra_vars `vpn_release_version` → `/etc/vpn-node-release.json` |

Проверить: `curl https://<host>/api/version` → `{"version": ..., "started_at":
..., "roles_version": ...}`.

**Времени выката в `.env` намеренно нет**: файл менялся бы на каждом прогоне
ansible и дёргал recreate всего стека даже когда ничего не изменилось. Вместо
него `/api/version` отдаёт время старта процесса — деплой контейнеры и так
пересоздаёт, так что это то же самое.

## 2. Версия кода на ноде

`site.yml` в `post_tasks` (то есть **только после успеха всех ролей**) пишет:

```json
{"version": "1.0.0", "applied_at": "2026-07-26T..."}
```

в `/etc/vpn-node-release.json`. Если прогон упал посередине — маркер остаётся
старым и честно показывает, что нода не догналась. При ручном прогоне ansible
без `vpn_release_version` маркер не трогается (чтобы не затереть реальную
версию заглушкой).

Расхождение «код на ноде» ≠ «код у нас» означает: после выката ноду ещё не
перекатывали. Лечится полным бутстрапом (кнопка на странице Nodes).

## 3. Версии бинарей на ноде

Тик **`tick-node-versions`** (раз в час, `NODE_VERSIONS_INTERVAL`) обходит
активные ноды по SSH и снимает `xray version`, `hysteria version` и маркер выше
в колонки `vpn_nodes.xray_version` / `hysteria_version` / `release_version` /
`versions_checked_at`. Все команды идут одним подключением; отсутствие бинаря
(нода без hy2) не мешает снять остальные версии.

Почему SSH, а не ansible: периодический ansible-фанаут идёт через семафор
провижининга (`MAX_CONCURRENT_ANSIBLE=3`) и выедал бы слоты у горячего пути
выдачи конфигов. Тот же приём уже используется сбором трафика.

Пустое значение не затирает известное: временно недоступная нода не должна
выглядеть как «версия пропала», у неё просто не обновляется
`versions_checked_at`.

## 4. Upstream-версии

Тик **`tick-xray-upstream`** (раз в 6 часов, `XRAY_UPSTREAM_INTERVAL`) проходит по
**обоим** продуктам — XTLS/Xray-core и apernet/hysteria, — кэширует последний
релиз каждого в таблицу `software_releases` (по строке на продукт) и пушит админу
в Telegram отдельным сообщением на продукт, когда:

* наш пин (`xray_core_version` в `roles/xray_core/defaults/main.yml`) отстал от
  upstream, либо
* какие-то ноды отстали от пина.

Дедуп — по тройке (продукт, upstream, пин) с окном в неделю: пока не вышел новый
релиз и не сменился пин, повторных пушей нет.

⚠️ Тег релиза hysteria — `app/vX.Y.Z` (монорепа app+core), в пине мы храним
версию без префикса, а в URL слэш экранируется как `%2F`. Нормализация срезает
и `app/`, и `v` — иначе сравнение с пином давало бы вечный ложный дрейф.

Список отставших нод в ключ дедупа не входит специально — иначе каждая
обновлённая нода порождала бы новый пуш про остальные.

### Почему апгрейд не автоматический

`xray_core_sha256` (и симметрично `hysteria2_sha256`) пинится **парой** к
версии. Тик, который «сам подтянул бы latest», поменяв только версию, положил бы
установку на всём флоте: fetch-скрипт
перебирает источники и каждый отвергает по несовпадению хэша. Поэтому бамп пина —
человеческое решение: правим обе переменные в роли, коммитим, деплоим.

⚠️ Перед раскаткой новой версии на RU-ноды нужно бампнуть соответствующий список
в `roles/mgmt_mirror/files/refresh-assets.sh` (`XRAY_VERSIONS` /
`HYSTERIA_VERSIONS`): для нод за заблокированным GitHub mgmt-зеркало —
единственный рабочий источник (ghproxy.com мёртв). Проверить, что зеркало реально
раздаёт нужную версию, можно так:

```bash
curl -sI http://<mgmt>:8090/xray/Xray-linux-64-<ver>.zip | head -n1
curl -sI http://<mgmt>:8090/hysteria/hysteria-linux-amd64-<ver> | head -n1
```

## Про hysteria отдельно

До 2026-07-26 версия hysteria не пинилась вообще: роль ставила
`bash <(curl -fsSL https://get.hy2.sh/)` и **только если бинаря нет**. Нода
получала latest на день своего рождения, обновить его роль не могла в принципе, а
разъезд версий по флоту был невидим.

Что изменилось: бинарь ставит наш `hysteria-fetch.sh` (зеркало → GitHub, sha256,
сверка фактической версии после установки) по пину из
`roles/install_hysteria2/defaults/main.yml`. Хэш берётся из `hashes.txt` релиза:

```bash
curl -sSL https://github.com/apernet/hysteria/releases/download/app%2Fv2.10.0/hashes.txt \
  | grep 'hysteria-linux-amd64$'
```

**Возвращать upstream-installer нельзя**: при повторном запуске он перезаписывает
наш systemd-юнит и переводит сервис на непривилегированного пользователя
`hysteria`, а `/etc/hysteria` (0750 root) и LE-ключ он прочитать не сможет — hy2
ляжет на всём флоте. Наш путь трогает только сам бинарь.

Пер-юзерные учётки (`auth.userpass`) живут в `/etc/hysteria/config.yaml` и
единственным источником истины остаются они. Точечный апгрейд конфиг не
перерендеривает, поэтому доступ клиентов не задевает.

## Как обновить бинари на нодах

Три пути, все из админки:

* **«Обновить hysteria»** — точечно: `playbooks/upgrade_hysteria.yml` подключает
  только бинарную часть роли (`tasks_from: binary`). Рестарт демона рвёт активные
  QUIC-сессии — клиент поднимает их заново сам, но это заметнее, чем 100 мс у
  xray (у UDP нет TCP-retransmit, который бы это замаскировал). На нодах без hy2
  кнопки нет.
* **«Обновить xray»** — точечно: гоняется только `playbooks/upgrade_xray.yml`
  (роль `xray_core`), ~30-60 с. `config.json` не перерендеривается, клиенты ноды
  остаются на месте. Рестарт ядра рвёт живые соединения примерно на 100 мс —
  клиенты переподключаются сами. Есть на странице Версии (по одной ноде, по
  выбранным, «все отставшие») и в раскрытой строке ноды на Nodes.
* **«Перекатать ноду»** (полный bootstrap, уже был) — 5-8 минут, приводит ноду в
  целевое состояние целиком, включая маркер версии кода.

API: `POST /api/nodes/{id}/upgrade-xray`, `POST /api/nodes/upgrade-xray`
(`{"node_ids": [...]}`), те же две ручки с `-hysteria`, сводка —
`GET /api/versions/overview`.

Действие в bypass-списке статус-переходов: провал доставки бинаря не обнуляет
health живой ноды и не промоутит `registering` → `active`.

## Порядок выката новой версии (xray или hysteria)

1. Узнать про релиз (пуш в Telegram или страница Версии).
2. Обновить **обе** переменные пина в defaults роли:
   * xray — `xray_core_version` + `xray_core_sha256` (sha от
     `Xray-linux-64.zip`);
   * hysteria — `hysteria2_version` + `hysteria2_sha256` (sha от
     `hysteria-linux-amd64`, берётся из `hashes.txt` релиза).
3. Бампнуть соответствующий список в `roles/mgmt_mirror/files/refresh-assets.sh`
   (`XRAY_VERSIONS` / `HYSTERIA_VERSIONS`) и прогнать
   `playbooks/mgmt_mirror.yml -e mgmt_mirror_force_refresh=true`, иначе RU-ноды
   не скачают.
4. Бампнуть `VERSION`, задеплоить (`--tags app`).
5. Обновить ноды — батчем со страницы Версии, начиная с малонаселённой.
