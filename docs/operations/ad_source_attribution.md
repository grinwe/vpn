# Атрибуция рекламных источников (deep-link метки)

**Цель.** Видеть, как ведут себя юзеры, пришедшие с конкретного рекламного
размещения: рекламщик/блогер кидает ссылку с меткой, человек заходит, и мы по
метке считаем воронку **старт → триал → оплата** и выручку. Без сторонней
аналитики — всё в нашей БД, привязано к `tg_id`.

## Как работает

Telegram deep-link старт-параметр = нативный UTM:

```
t.me/<бот>?start=<МЕТКА>      напр.  t.me/grnvpn_bot?start=tg_blogger1
```

Юзер жмёт Start → бот получает `/start <МЕТКА>` → метка пишется в БД как источник
этого юзера.

- **Неймспейсы в `/start`** (`bot/handlers.py`): `ref_<code>` — реферал ЧЕЛОВЕКА
  (идёт в `User.referred_by_id` + бонусы); **любой другой непустой payload** —
  рекламная МЕТКА (источник), идёт в `User.source`. Это разные вещи: реферал
  платит человеку, метка — чистая аналитика размещения.
- **First-touch:** `User.source` (`models.py`, миграция `0054`) ставится ОДИН раз
  при первом `/start` с меткой (как `referred_by_id`) — органик-старт без метки
  не блокирует атрибуцию при последующем заходе по рекламе.
- **Санитайз:** метка чистится до `[A-Za-z0-9_-]`, ≤64 символов
  (`api_extensions._clean_source`) — ровно допустимый алфавит старт-параметра
  Telegram; мусор отбрасывается (source остаётся NULL).
- **Reserved-ключи:** служебные deep-link'и (`ref_*` — реферал; `support` —
  из вебаппа, `Help.tsx`) НЕ считаются рекламными метками (`_RESERVED_SOURCES`).
  При добавлении нового служебного `?start=<ключ>` — занести его туда, иначе
  попадёт в рекламную воронку.

## Воронка

`GET /api/admin/ad-sources` (admin) — на каждую метку:

| Этап | Сигнал |
|------|--------|
| **started** | юзеров с этой меткой (`User.source = tag`) |
| **trial** | из них активировали триал (`User.trial_activated_at`) |
| **paid** | из них сделали ≥1 реальную оплату (`BalanceTransaction kind=topup`) |
| **revenue** | сумма topup'ов с метки |

Считается ДВУМЯ запросами (started/trial по `users`; paid/revenue по
topup-транзакциям) с мержем в Python — join транзакций к `users` раздул бы
счётчик `started` кратно числу транзакций юзера (join-fanout).

**Бот:** `/adstats` (admin) — показывает воронку по меткам + конверсию + выручку.

## Управляемые ссылки (админка)

`AdLink` (таблица `ad_links`, миграция `0055`) — управляемая рекламная ссылка:
`name` (ярлык для админа) + `tag` (метка) + `is_active`. Это слой управления над
free-form source-меткой; ad-hoc метки (без `AdLink`) продолжают атрибутироваться.

- **Admin SPA, вкладка «Реклама»** (`admin/src/pages/AdLinks.tsx`): создать ссылку
  (имя + метка, пустая → авто `ad_<random>`), скопировать `t.me/bot?start=<tag>`,
  видеть **живую воронку** (рефреш 15с: старт/триал/оплата/конверсия/выручка),
  вкл/выкл, править, удалять.
- **API** (`api_extensions.py`, admin): `GET/POST /admin/ad-links`,
  `PATCH/DELETE /admin/ad-links/{id}`. Листинг отдаёт воронку (`_compute_source_funnel`).
- **`is_active=false`** = новые заходы по метке БОЛЬШЕ не атрибутируются (гейт в
  `register_user`); историческая стата сохраняется. Удаление убирает ярлык, но
  `User.source`-строки остаются (метка покажется в `/adstats` как ad-hoc).
- **`tag` неизменяем** после создания (иначе осиротит накопленную статистику).

## Под несколько размещений

Делаешь разные ссылки с разными метками (`tg_blogger1`, `tt_ceprem_test1`,
`vk_promo`) → сравниваешь в админке/`/adstats`, что окупается.

## Чего пока НЕТ (бэклог)

- Несколько ИМЕНОВАННЫХ меток на одного рекламщика как сущность (сейчас метка —
  свободная строка, без отдельной таблицы кампаний).
- Учёт КЛИКОВ (только старт бота, не переход по ссылке — Telegram не отдаёт клик
  до Start).
- Леджер переходов (мульти-тач, смена источника) — сейчас только first-touch.
- Выплаты/комиссии рекламщикам (реферальные бонусы — отдельный механизм).
- Анти-фрод (self-referral / мульти-аккаунты).
