# Архитектурный обзор и текущие риски

## Backend: доменная модель и миграции
- **Расширенная модель добавлена, но миграции остаются упрощёнными.** Таблицы `vpn_nodes`, `vpn_configs`, `devices`, `provisioning_tasks`, `audit_logs` добавлены через `Base.metadata.create_all`, что не покрывает эволюцию схемы и откаты. Требуется полноценный Alembic-флоу с версионированием и автоматическими апгрейдами, иначе прод-данные сложно менять без простоя. 【F:backend/app/models.py†L24-L209】【F:backend/app/migrations.py†L6-L15】
- **Трафиковые и ресурсные лимиты не учитываются оперативно.** В `Subscription` и `Plan` есть поля `traffic_limit_mb` и `traffic_used_mb`, но нет фонового обновления (нет коллекторов/биллинг-джобов). Это позволяет пользователям превышать лимит без блокировки. Нужен сбор метрик с нод и периодический апдейт лимитов. 【F:backend/app/models.py†L102-L150】
- **Учётные данные устройств не ревокируются в базе.** `Credential` имеет `revoked_at`, но нет сервисных методов для отзыва/ротации паролей, поэтому компрометация пароля не закрывается автоматически. Требуется API/джобы для перевыпуска и пометки невалидных секретов. 【F:backend/app/models.py†L150-L183】

## Backend API и валидация
- **Нет аутентификации/авторизации на админских методах.** Эндпойнты `/api/nodes`, `/api/invoices/{id}/mark_paid`, `/api/provisioning/tasks` открыты без токенов или ролевой модели, что создаёт риск несанкционированного управления нодами и платежами. Нужно ввести хотя бы простую token-based auth и разграничение ролей. 【F:backend/app/api.py†L65-L180】
- **Провижининг деактивации частично заглушен.** Запрос `/subscriptions/{id}/disable` ставит задачу с `state=absent`, но не гарантирует, что нужный `username`/порт доступны: берётся только первый `device`. Следует хранить и передавать всю связку `device->config` для массового отзыва. 【F:backend/app/api.py†L208-L224】
- **Отсутствует пагинация и фильтры для списка задач/нод.** `/api/provisioning/tasks` и `/api/nodes` возвращают полный список, что может перегружать клиента и БД. Добавить параметры `limit/offset` и фильтры по статусу/региону. 【F:backend/app/api.py†L131-L150】

## Провижининг
- **Зависимость от локально установленного Ansible.** `ProvisioningOrchestrator` вызывает `ansible-playbook` через `subprocess` без управления окружением/виртуальным инвентарём. В контейнере backend Ansible может отсутствовать. Требуется отдельный воркер/runner-образ с ansible или RPC в CI/CD. 【F:backend/app/services/provisioning.py†L28-L121】
- **Идempotency частично обеспечена.** Плейбук `provision_device.yml` вызывает manage-скрипт, но не проверяет существование пользователя/возвращаемый stdout для записи кредов. Нужно доработать playbook для идемпотентных операций и обратной синхронизации (например, писать результат в файл и считывать его backend-ом). 【F:infra/ansible/playbooks/provision_device.yml†L1-L24】
- **Отсутствует очередь задач/ретраи.** ProvisioningTask выполняется синхронно в HTTP-запросе, что блокирует клиента и не даёт повторять с бэк-оффом. Нужен фоновый воркер (Celery/RQ) или хотя бы cron-ретраи по статусу `failed`. 【F:backend/app/api.py†L100-L128】【F:backend/app/services/provisioning.py†L61-L118】

## Ansible / инфраструктура
- **Инвентарь пока статический.** Генерация inventory для одного хоста есть в `build_inventory_for_node`, но playbooks по умолчанию используют статический `inventories/prod/hosts.yml`. Нужно описать, как backend генерирует полный инвентарь из БД (pools/регион/теги) и передаёт его runner-у. 【F:backend/app/services/ansible_runner.py†L11-L46】【F:infra/ansible/inventories/prod/hosts.yml†L1-L15】
- **Роли базовой безопасности не применяются к db_host.** Новый `bootstrap_node` настраивает UFW/SSH для `vpn_nodes`, но хост БД использует старый `db_host` без аналогичных харденингов. Добавить reuse ролей или отдельный hardening для управляющего хоста. 【F:infra/ansible/site.yml†L1-L9】【F:infra/ansible/roles/bootstrap_node/tasks/main.yml†L1-L49】
- **Нет Ansible-lint/CI.** В репозитории нет workflow для `ansible-lint`, что затрудняет контроль качества плейбуков. Следует добавить GitHub Actions для линтинга и тестовых прогонов. (общая рекомендация)

## Telegram-бот
- **Нет обработчиков ошибок/ретраев к backend.** `_fetch_json` не выполняет повторные попытки и не различает коды ошибок, пользователи получают общие сообщения. Требуются backoff-ретраи и детальные ответы по валидации/статусам провижининга. 【F:bot/handlers.py†L16-L118】
- **Авторизация админов по статическому списку.** `ADMIN_IDS` хранится в env, но нет проверки подписи или ролей из backend. Лучше запрашивать разрешения из API или JWT. 【F:bot/config.py†L1-L8】【F:bot/handlers.py†L9-L33】

## Безопасность
- **Секреты по умолчанию заданы жёстко.** `DATABASE_URL`, `POSTGRES_PASSWORD`, `BOT_TOKEN` имеют дефолтные значения в compose/конфиге. Их нужно вынести в `.env`/секреты CI и описать требования к ротации ключей SSH. 【F:docker-compose.yml†L1-L24】【F:backend/app/db.py†L1-L10】【F:bot/config.py†L1-L8】
- **Нет ограничений по API-частоте или CSRF-защиты.** Backend открыт без rate limiting; для публичного API стоит добавить throttling (например, через proxy/API gateway) и базовую аутентификацию. (общая рекомендация)

## Наблюдаемость
- **Метрики минимальны.** Добавлен счётчик `vpn_requests_total`, но нет пер-пути латенций и статусов, а health-check не включает проверку очереди провижининга. Следует интегрировать middleware с гистограммами и расширить `/healthz` проверкой внешних зависимостей. 【F:backend/app/main.py†L1-L35】【F:backend/app/api.py†L73-L89】
- **Нет логирования аудита в бот/infra.** AuditLog хранится только на backend, но операции Ansible/бота не логируются централизованно. Нужен единый формат логов и сборщик (ELK/Vector). 【F:backend/app/models.py†L185-L209】

## CI/CD
- **Автотесты и статические анализаторы отсутствуют.** Нет pipeline, который бы запускал unit-тесты, ruff/mypy или проверял сборку docker-compose. Это снижает надёжность релизов. (общая рекомендация)
- **Нет публикации образов.** Backend/бот собираются только локально/через Ansible. Нужна GitHub Actions для сборки и пуша контейнеров в регистр и их дальнейшего развёртывания. (общая рекомендация)

## Дополнительные наблюдения (после внедрения MVP-улучшений)
- **Админские маршруты теперь закрыты shared-токеном.** Эндпойнты управления нодами, инвойсами, платежами и задачами требуют заголовок `X-Admin-Token`; актор для аудита задаётся через `X-Admin-Actor`. Ошибочное отсутствие секрета приводит к 503, что защищает от случайного старта без конфигурации. 【F:backend/app/api.py†L20-L60】【F:backend/app/config.py†L1-L22】
- **Провижининг фиксирует stdout/stderr и хранит статусы.** Ansible-запуски оборачиваются в безопасный раннер, вывод сохраняется в `result`, задачи можно перезапускать асинхронно через отдельный эндпойнт. 【F:backend/app/services/provisioning.py†L13-L168】【F:backend/app/api.py†L102-L165】
- **Healthcheck и метрики расширены.** `/healthz?deep=true` проверяет наличие каталога Ansible, а Prometheus-счётчики добавляют статусы ответов и provisioning-задач. 【F:backend/app/api.py†L65-L95】【F:backend/app/main.py†L1-L31】
- **Миграции получили версионирование.** Добавлена таблица `schema_migrations` и миграция `0001_initial`, что убирает `create_all` без контроля версии. 【F:backend/app/migrations.py†L1-L55】
- **Бот читает админов и токен из окружения.** Ошибки бэкенда теперь отображаются человеку вместо молчаливых таймаутов. 【F:bot/config.py†L1-L12】【F:bot/handlers.py†L1-L120】
